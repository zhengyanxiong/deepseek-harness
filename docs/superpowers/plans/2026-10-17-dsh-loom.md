# Loom 首版分阶段实现计划

> **For agentic workers:** 使用 executing-plans 按阶段执行；用户已经批准产品设计和开始开发，不再重复请求开始许可。

**Goal:** 在独立 Loom worktree 实现项目版本、固定任务基线、同任务工作区复用与完整原生会话工作台。

**Architecture:** 使用独立 `loom/` 插件包，与 `workbench/` 并列。业务状态和 Git 操作由 Host 所有；Client 只展示结果并调用操作。任务状态转换使用纯函数，持久化与执行权在服务层串行协调。

**Tech Stack:** TypeScript、Cordis、React、DSH slots、Git worktree、Vitest。

## 文件职责与实施顺序

- `loom/src/domain/task.ts`：任务轮次转换、不可变 Lock、会话关联和工作区复用约束。
- `loom/tests/task.spec.ts`：纯领域不变量；不创建 Git 仓库或启动服务。
- `loom/vitest.config.ts`：限定 Loom 测试，使用仓库路径解析。
- 后续按接口核对结果分别添加配置解析、Host 存储、Git 适配、执行权、原生会话绑定与 UI；这些模块不得把状态转换散落进组件。

## 第一增量：任务与轮次

- [x] 先写测试：首次执行固定 Lock；后续会话仍指向原工作区；外部修改传入 Lock 不污染已开始轮次。
- [x] 验证首次测试失败源自未实现任务 API。
- [x] 实现 `createTask`、`startAttempt`、`attachSession`、`transitionTask`，错误以稳定 code 表达，不在领域层输出 UI 文案。
- [x] 测试失败任务重启保留历史；换 Lock 不能复用原工作区；同版本校验；终态需要 human actor。
- [x] 运行 `pnpm exec vitest run --config loom/vitest.config.ts`，核对完整输出和退出码。

测试用例核心断言：

```text
first = startAttempt(task, lockA, workspaceA)
continued = attachSession(attachSession(first, sessionA), sessionB)
continued.attempts.length === 1
continued.attempts[0].workspaceId === workspaceA
continued.attempts[0].sessionIds === [sessionA, sessionB]
```

本增量不声称实现了运行中任务互斥：领域函数只验证状态，Host 服务还必须对持久化事务和操作进行串行控制。

## 后续验收顺序

1. 配置解析：验证版本和仓库引用，拒绝越界、重叠路径；解析真实 commit 并冻结快照。
2. 持久化：项目、Lock、任务轮次及审计；进程重启保留数据；失败写入不发布成功状态。
3. Git：临时本地仓库集成测试；全仓库准备、回滚只清理本次创建的资源；保持未提交成果。
4. 执行权：先启动占用测试，再实现等待和停止确认后的接管；状态未知不得授予执行权。
5. 原生会话：通过 retained SessionReference 和 SessionProvider 绑定，使用 `conversation.content` 工厂而非复制输入框；卸载释放引用。
6. UI：项目/版本/任务表单、完整三栏工作台、看板、默认折叠底部及原生 Diff；真实 Host 数据，不用模拟值替代。
7. 集成：首次执行到多会话接续、验收和失败重启；隔离开发实例验证，不安装到当前部署 profile。

## 已核对接口依据

- Live `Slots.listSubTree(main)`：支持独立 `loom` key；非 conversation key 不自动获得会话绑定。
- Live Client Service directory：`sessions.retain`、`sessions.binding`、`workspaces.create` 与 `uiWorkspace` 已存在，使用前仍核对具体类型与释放语义。
- 源码参考：`workbench/src/client/conversation/ConversationEmbed.tsx` 使用 `conversation.content` 工厂与 `conversation.session` chat 视图。

## 原生 Diff 接入差异

`ui-deliverables` 当前仅将 `ReviewTab` 注册到 `sidebar.right.pane.tab` 的 `changes-review` key；它按 Session 单轮 seq/index 读取变更，不是可嵌入工厂。Loom 不得直接导入其运行时组件或重复声明原生槽。下一阶段需在 Loom worktree 的原生插件中提取工厂，保留原侧栏适配，再由 Loom 使用该工厂。多仓库工作区根目录不是 Git 仓库，当前原生 recorder 仅定位所在仓库，不能提供子仓库汇总或任务 Lock 到当前工作树的比较；需补充逐仓库数据服务与集成测试。

## 远程接口接入差异

Loom 是独立外部 bundle，不是 pnpm workspace 包；自动生成的 `ctx.remote.loom` 需要 bundle 自备生成产物。已选定并执行路径 A：

- 生成器新增 `WorkspaceAnalyzerOptions.packageRoots`（并入发现缓存键），允许把工作区内额外目录（如根级 `loom/`）登记为包根；越界根在构造时抛错。`WorkspaceTypertGeneratorOptions` 同步透传 `packageRoots`、`hostConfig`、`clientConfig`。
- Loom 提供自己的 Typert 聚合 config：`loom/tsconfig.typert.host.json`（引用 `packages/typert/protocol` 以便识别 `@Remote`/`@RemoteScope` 符号，再引用只含 `src` 的 `loom/tsconfig.face.host.json`）与 `loom/tsconfig.typert.client.json`。测试源会引入 registry 等未登记包，因此生成用 `tsconfig.face.*` 而不是 `tsconfig.host.json`/`tsconfig.client.json`。
- `loom/scripts/generate-typert.ts` 以 `WorkspaceTypertGenerator(root, { packageRoots: ['loom'], hostConfig, clientConfig })` 生成并 `writeWorkspaceArtifacts`，只发出 `dsh-loom`；产物为 `lib/typert.host.js`、`lib/typert.remote-client.{js,d.ts,d.ts.map}`。`pnpm --dir loom run generate` 前置到 `build`，重复执行字节一致。
- Loom 公开 `./typert`、`./remote`、`./types` 导出；`./types` 的 `types` 指向 `src/types.ts`（唯一来源，同时满足生成器“边界类型须由公开非根子路径导出”的约束）。Host 端点参数从 `unknown` 收紧为 `src/types.ts` 中的请求类型，运行时仍由 zod 严格校验。
- 客户端 `src/client/index.ts` 在 effect 中 `ctx.remote.$mount(contribution)`；页面注册由 `ctx.inject(['slots','locale','sessions','remote.loom'], …)` 建立的消费 fiber 完成，`loadSnapshot` 直接读取 `remote.loom.snapshot()`。`LoomPanel` 渲染项目、版本、看板与任务详情。
- `loom/cordis.patch.yml` 的 bundle 行默认 `catalogFile: !!js dshHomePath('loom/catalog.json')`；Host 服务在初始化前递归创建缺失的父目录。
- 隔离 profile 端到端验证（`DSH_HOME=/tmp/dsh-loom-verify`，端口 3099，未触碰运行中的部署 profile）：`dsh plugin --profile loom-dev add <loom>` 安装成功后，`--dump-config` 显示 bundle 层与 `!!js` 配置；启动探针插件读到 `dsh-loom#host` 包记录与全部 9 个 `loom/*` endpoint，直接调用服务被 `owner_required` 拒绝；浏览器打开页面后侧栏出现 Loom 项，点击后发出 `POST /api/loom/snapshot` 并收到 `200 {"ok":true,…}`，页面渲染“No projects yet.”，无 console 错误。
- 页面接入真实创建闭环：`LoomForms.tsx` 提供项目（名称 + 仓库行）、版本（名称 + 每仓库引用）、任务（标题）表单与 Lock 生成按钮；纯函数 `projectRequest`/`versionRequest`/`taskRequest` 负责去空格与必填校验，`LoomPanel` 在创建成功后重新读取 `snapshot`。
- 隔离 profile 浏览器二次验证：通过页面表单依次发出 `createProject`、`createVersion`、`createTask`，每次均返回 `200 {"ok":true,…}` 并刷新 `snapshot`；项目名、版本名出现于侧栏，任务出现于看板；无 console 错误。
- 环境说明：该检出中 `packages/client/jev-gate-ui/tsdown.config.ts` 调用 `clientBundle('jev-gate', …)` 而非包目录，`pnpm run build:artifacts` 因此在该包失败；隔离实例改为复用部署检出同提交的 `lib/` 与 `apps/web/dist` 产物完成验证，未修改部署检出与运行中的 profile。
- Host 新增 `prepareWorkspace` 端点：按 version 的 Lock 把每个仓库以 detached worktree 检出到指定根目录，再登记工作区；新请求类型 `PrepareWorkspaceRequest`，生成产物随之更新。Catalog 在创建前校验版本/Lock/路径，重复路径返回 `workspace_path_registered`。
- 客户端 `LoomExecution.tsx`：pending/failed 任务选择 Lock 与工作区根目录后依次执行 `prepareWorkspace` → `startAttempt` → 原生 `workspaces.create` → `sessions.create` → `attachSession`；running 状态提供“提交验收/确认失败”，review 状态提供“确认完成/继续修改/确认失败”，并可复用工作区继续创建会话。`LoomPanel` 把看板选中的任务与刷新后的 snapshot 同步，避免详情展示过期状态。
- 隔离 profile 浏览器完整闭环验证：真实本地仓库（commit `eed9c50…`）→ 页面生成 Lock → `prepareWorkspace`（`/tmp/loom-browser-ws/web` 检出为该 commit）→ `startAttempt` → `attachSession`（原生会话 `session-2e89…`）→ `transitionTask(review)` → `transitionTask(completed)`，全部 `200 ok`，目录中记录 status `completed`、1 个 attempt、1 个会话，无 console 错误。
- 原生 Diff 复用落地：`ui-deliverables` 新增并注册 `deliverables.fileDiff` Factory（调用方提供已算好的 hunks/二进制状态与 split/wrap/retry，字典与样式留在该包）；Loom 新增 `workspaceChanges` 端点，按 Lock 提交读取每个仓库的 tracked 改动与未跟踪文件（统一 hunk 解析），底部 Diff 面板经 `renderFactorySlot` 渲染原生 `FileDiff`。
- 隔离 profile 浏览器验证 Diff：工作区修改 + 未跟踪文件后，面板列出 `index.js`、`notes.txt` 并显示 `@@` hunk 与新增/删除计数；首次暴露缺少 `path` 导致原生 `TextDiff` 崩溃，补齐后无 console 错误。
- 已验证：生成器全量测试 248 通过；`ui-deliverables` 178 测试通过、client tsc 通过；Loom domain/host/client 三面 tsc 通过；Loom 110 测试通过；`pnpm --dir loom build` Client 123.57 kB。未完成：工作区保留/清理与执行权交接、terminal/tests/audit/costs 底部面板、Agent 执行入口的实时执行权拦截。
