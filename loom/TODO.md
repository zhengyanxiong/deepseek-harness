本文件只记录尚未完成的产品能力，不重复已经闭环的项目、版本、任务、Lock、工作区、原生会话、Diff、执行权、清理和删除能力。优先级最高的是**版本级共享上下文设计**（P0-0）：先完成设计评审，再实现。

## P0：首版闭环

### P0-0 版本级共享上下文（最高优先级，先设计）

**问题**

- `VersionRecord` 目前只有 `id`、`projectId`、`name` 和 `sources`，没有版本说明或版本级上下文。
- 右侧上下文面板按当前任务展示，版本信息只是任务上下文的一部分；同一版本下的多个任务、多个执行轮次之间没有共享的、可注入的事实。
- 原生会话没有版本级动态上下文。Agent 只能从任务描述、工作区路径和当前对话推断版本范围，容易重复实现、改动冲突或误解 Lock 基线。
- 版本详情页、Lock 历史和版本内任务视图都还没有落地，用户也无法在进入任务前确认这一版的完整内容。

**目标**

同一版本下的所有任务和会话共享一份只读、可解释、受控的版本上下文；任务自身的上下文、会话历史和代码工作区仍相互独立。版本上下文不是共享聊天记录，也不是共享工作区文件；同一任务跨会话的续接仍由交接摘要（P0-7）负责，两者不能混成一份对话历史。

建议数据流：

```text
CatalogSnapshot ──derive──> VersionContext 只读视图
                                  ├──> 客户端版本上下文面板 / 版本详情页
                                  └──> Host 原生动态上下文注入 ──> 绑定该版本任务的 Session
```

**建议的范围与字段**

- 版本身份：版本 ID、名称、所属项目和项目名。
- 仓库基线：每个仓库来源、仓库内目录、版本 ref、所选 Lock 的精确 commit；如果同一版本存在多个 Lock，分别列出各任务固定到的 Lock。
- 业务模块：版本内可用模块及其所属仓库；模块只用于聚焦上下文，不作为文件权限。
- 人类撰写的版本说明：本版本的目标、范围、验收口径、禁止事项和跨任务约定。
- 同版本任务摘要：任务 ID、标题、状态、模块、当前轮次、最近 Lock、工作区分支和占用情况。默认不放入其他任务的完整描述或会话内容。
- 当前执行状态：哪些工作区被占用、等待队列是否存在、是否有未确认的接管；只描述事实，不授予执行权。
- 不包含：其他 Session 的完整对话、工具输出、私密附件、跨版本内容，以及伪造的进度或测试指标。

**数据模型建议**

- 给 `VersionRecord` 增加可选的 `description`（或命名更明确的 `context`）字段，默认空字符串，限制长度；旧 catalog 缺少该字段时按空字符串读取，写回兼容。
- 复用已有的 `version.description` 文案，在版本创建/编辑表单中增加说明输入；只保存配置，不触发 Git 或脚本。
- `VersionContext` 作为从 `CatalogSnapshot` 派生的只读模型，不持久化生成后的文本；避免在版本、任务、Lock 更新后维护多份副本。
- 需要为 Lock 增加生成时间，才能在同一版本多个 Lock 的上下文中正确排序和展示历史；这会和 P0-5 的数据模型改动合并处理。

**原生会话注入**

- 优先使用 DSH 的 `systemPrompt.context` 动态上下文机制：按 Session 找到已绑定的任务，再找到任务所属版本，生成紧凑的版本摘要；不复制聊天、不伪造用户消息。
- 版本归属必须从任务绑定关系推导，不能跟随 UI 当前选中的版本，否则切换顶层项目/版本会悄悄改变既有会话的上下文。
- 注入内容必须模型可见且可追溯；实现前确认该动态上下文会进入原生会话记录。若当前接口不能保证记录，先完成 Host 只读视图和 UI，注入延期，不采用不可见注入。
- 生成过程只读缓存快照，不在模型请求路径上执行 Git 或文件 I/O；catalog 写入后更新快照。
- 文本需要长度上限、顺序稳定、无重复任务信息；版本说明作为人类提供的参考数据，明确不是系统指令，不覆盖 DSH 的安全策略和当前任务指令。
- 未绑定任务、跨版本、已清理或无法解析版本的 Session 不注入版本上下文。临时会话默认不继承版本上下文，除非后续明确把它绑定到版本。

**UI 建议**

- 右侧新增“版本上下文”区域，展示版本名称、项目、仓库基线、模块、版本说明、同版本任务和当前占用；任务上下文继续独立展示。
- 点击左侧版本时提供版本详情页：版本配置、参与仓库、模块、Lock 历史、版本内任务；这是设计文档中已列出的首版能力。
- 版本创建/编辑表单提供版本说明；任务创建和开始执行前显示将继承的版本摘要，避免用户在不知道基线的情况下启动会话。
- 不显示模拟的“共享上下文”“已完成”等状态；没有真实 Lock 或任务时显示明确的空状态。

**边界与规则**

- 版本上下文只读，不改变执行权、工作区所有权或文件权限。
- 同版本任务默认仍使用独立工作区；共享工作区必须是用户显式选择，并保留现有警告。
- 版本上下文不替代 Diff、测试结果或人工验收；摘要不是代码状态的证明。
- 不把版本说明当成跨任务的强制指令；需要执行的约定应由任务描述和用户当前指令表达。

**验收标准**

- 在版本 V1 的任务会话中，模型请求包含 V1 的项目、仓库、Lock、版本说明和同版本任务摘要；不包含 V2 或跨项目内容。
- 切换 UI 上的当前版本不会改变已绑定会话的版本上下文。
- 修改版本说明后，新的模型请求反映新内容，无需重启 Host。
- 未绑定任务、临时会话和无版本信息的 Session 不出现版本上下文。
- 上下文长度有上限，仓库和任务增多时截断规则确定且可解释。
- 版本详情页和右侧上下文读到同一份派生数据；UI 测试覆盖空状态、多个 Lock、多个任务和截断情况。
- 原生会话记录可核对注入事实；测试覆盖注入内容、作用域隔离和重复请求。

**开放问题**

- 同版本其他任务的完整描述是否进入上下文，还是只放标题、状态和模块？
- 版本说明只允许人类编辑，还是允许 Agent 追加“决策/阻塞”条目？如果允许 Agent 写入，需要审计和人工确认。
- 版本上下文是一份共享摘要，还是“共享基线 + 当前任务覆盖层”两层？建议先做共享视图，任务差异继续由任务详情承担。
- 临时会话是否应绑定到版本并继承上下文？当前设计倾向默认独立工作区，不自动继承。
- 版本说明是自由文本还是结构化字段（目标、范围、验收、禁止事项）？结构化字段更利于注入和校验，但首版可先用受限自由文本。

### P0-1 任务内会话列表与切换

- [ ] 在左侧任务节点下展示全部执行轮次和轮次内会话，而不是只自动选中最新会话。
- [ ] 支持在任务内打开、切换、继续旧会话；切换后保留原生 `SessionReference`，不复制会话历史。
- [ ] 每个会话显示真实状态（运行中、空闲、不可用）和所属轮次；不可用会话给出原因和恢复入口。

现状：`LoomPanel.tsx` 的 `selectTask()` 只选 `attempts.at(-1)?.sessionIds.at(-1)`；`boundSessions` 已有全量数据，但 UI 没有任务内会话列表；`looseSessions` 明确排除已绑定会话，因此旧会话无法从任务详情重新进入。看板右侧只能点击仍在运行的会话。

验收：同一任务有两个或更多轮次/会话时可全部找到；切换会话不新增轮次或 worktree；会话不可用时显示可操作的失败提示。

### P0-2 验收闭环、结果摘要与 Agent 接口

- [ ] 任务详情展示当前轮次的结果摘要：Agent 自述、完成项、未完成项、已知风险和影响范围。
- [ ] 展示可用的真实测试结果（有则显示，无则明确“未运行/无结果”，不能用示意数据）。
- [ ] 提供 Agent 侧工具：申请进入待验收、建议失败并给出原因；完成和失败仍必须由用户确认。
- [ ] 验收前把「Agent 摘要 + 代码变更 + 测试结果」放在同一决策区域，并明确目标 Diff 的 Lock 基线。
- [ ] 记录验收/失败确认的 actor、时间和依据，供审计查看。

现状：`LoomExecution.tsx` 只有“提交验收/确认完成/确认失败”按钮；任务没有结构化结果字段；Host 没有面向 Agent 的 Workloom 工具；`task.humanOnly` 文案存在但界面未使用。

验收：Agent 可以建议验收/失败但不能代替人类完成；用户能在确认前看到真实的摘要、Diff 和测试状态；没有测试结果时显示明确的缺失状态。

### P0-3 临时会话独立工作区与执行权安全

- [ ] 临时会话默认使用独立工作区，而不是直接在最新活跃任务工作区中创建。
- [ ] 如果允许临时会话复用 Loom 工作区，必须把它纳入执行权获取、等待和释放流程；未绑定 Session 不能直接写共享工作区。
- [ ] 清理工作区前同时检查任务状态和执行权 owner，不能只检查 `task.status === 'running'`。

现状：`openTemporary()` 在最新活跃工作区创建会话，但没有 `attachSession`，因此不会经过 `admitExecution` 的工具门禁，可能与任务会话同时写同一工作区；工作区清理只检查运行中任务，没有检查 review/completed 任务上仍存在的执行 owner。

验收：临时会话与任务会话不能无提示地并发写同一工作区；清理被占用的工作区会给出具体阻塞原因；临时会话无工作区时创建独立工作区或明确失败。

### P0-5 Lock 历史与详情

- [ ] 版本详情中列出全部不可变 Lock：生成时间、每个仓库的 ref、精确 commit、来源任务和是否仍被工作区引用。
- [ ] 任务开始页可选择同版本历史 Lock，并明确选择后对工作区复用的影响。
- [ ] `Lock` 增加生成时间字段并完成旧 catalog 兼容迁移。

现状：`Lock` 只有 `id`、`versionId`、`repositories`；上下文只显示当前版本 Lock 数量和任务最近 commit；`lock.createdAt`、`lock.commit`、`lock.immutable` 文案没有被使用。

验收：同一版本多个 Lock 可区分、可追溯；旧 Lock 不因分支移动而改变；选择历史 Lock 时 UI 显示其精确提交。

### P0-6 准备工作区与清理的分步可观测性

- [ ] 准备工作区按仓库显示进度（等待、检出、完成、失败），支持部分失败后重试。
- [ ] 准备失败显示具体仓库、路径、Git 诊断和已创建资源的回滚结果，允许重试而不是只显示通用错误。
- [ ] 清理按仓库报告成功项和未完成项；部分失败时保留可再次清理的状态，不把整次操作折叠成 `workspace_cleanup_failed`。

现状：`prepareWorkspace` 是一次 Remote 调用，客户端只有一个 busy 状态；失败通常只显示通用错误。清理失败也只返回通用 code，缺少逐仓库结果。

验收：多仓库准备中一个仓库失败时，用户能知道其他仓库发生了什么、是否需要重试；清理部分失败后不会误报“已清理”。

### P0-7 接管交接摘要

- [ ] 记录摘要来源和接管确认，便于审计。

验收：用户确认接管前能看到可解释的交接信息；摘要缺失时明确提示，而不是制造虚假完成度。

### P0-8 失败反馈与静默错误

- [ ] 将已知错误 code 映射到本地化文案；未知错误保留 Host 诊断和可恢复入口。
- [ ] 加载、保存、保存成功和重试状态使用一致的可访问反馈。

现状：`transition()`、`moveTask()`、`openTemporary()` 等路径有只写注释的 `catch`，失败对用户不可见；这与设计要求的“失败提示包含影响范围和下一步”不一致。

验收：任意可触发操作失败时都有可见的、可操作的反馈；不再有静默吞错路径。

- 自动 commit、push 或 merge。
- 跨仓库原子提交。
- 复制一套原生聊天、工具卡片或审批系统。
- 操作系统级工作区独占；当前执行权只约束 DSH 管理的 Agent 工具调用。
- 用模拟数据冒充真实 Lock、测试、成本或 PR/CI 状态。
